You are running `/cadence:evidence` on behalf of a developer who just changed something in `@rolobits/is-human-cadence` and wants a record of what was actually observed, not a summary of what was built.

Their input is: `$ARGUMENTS`

If `$ARGUMENTS` is empty, stop immediately and print:

```
Usage: /cadence:evidence <the claim to evidence>

Examples:
  /cadence:evidence "the new burst metric does not regress human scores"
  /cadence:evidence "rolloverRate gating no longer inflates the constant-bot score"
  /cadence:evidence "the demo still scores a real typist above 0.70 on Safari"

Works out what each part of the claim is a claim about, runs it, and drafts a
report with a numbered item per sub-claim (ACCEPTED / REJECTED / EXERCISED /
BLOCKED). Nothing is written to .claude/worklog/ until you approve it.
```

The workflow has one strict human gate: **nothing is written to `.claude/worklog/` until the developer explicitly approves the draft.** Present it, stop, wait. "go" / "approved" / "write it" means write; anything else means iterate or cancel.

## Why this command exists

A change description says what should be true. What it cannot say, because it is written before the thing runs, is what happened when you actually did it: the score, the sample count, the spread across seeds, the event that carried `isTrusted: true`.

Every item must pass one test: **delete the claim, keep only this item — could someone still run the check and know what a pass looks like?** If an item could have been written by paraphrasing the change description without running anything, throw it out and go get real evidence.

This library makes an **accuracy claim** — it scores humans high and bots low — and nothing in the repo can check it. `DEFAULT_WEIGHTS` (`src/analyzer.ts:20`) was calibrated against the Aalto 168K-typist benchmark, and the runner for it lives in `validation/`, which is gitignored (`.gitignore:8`), absent from the repo, and whose `tsx` runner is not in `devDependencies`. So a weight retune can pass every check that exists here and be worse in the real world, and nothing would say so.

**A passing test says the fixtures still behave. It does not say the library got better.**

## The rule that matters most here

**A run against `tests/fixtures/` can never earn ACCEPTED.** It exercises the scoring maths against data this repo generated to match its own model of a human, and nothing else. `generateHumanLike` (`tests/fixtures/human-profiles.ts:25`) draws flights from `exp(4.5 + 0.6·Z)` — a log-normal — and `scoreFlightFit` scores flights by KS-testing them against a log-normal. The fixtures were written by the same person who wrote the metrics. Circularity is the whole problem.

Only **real keystrokes captured through real browser events**, or a **real external corpus**, can settle an accuracy row. Everything else is at most EXERCISED.

**`npm run check` is not evidence either.** `typecheck && lint && test && build` is a precondition — it says the change compiles and the 173 existing tests still pass. It is never a verdict on accuracy.

## Accuracy claims are distributions, not values

For any row about scoring, the contract is a **score distribution over many samples**, not one score. An item showing a single score has proven nothing — a seed can be lucky. Report `n`, the median and the spread, and say which fixture generator or corpus produced them.

Measured on this machine, 50 seeds each, `analyze()` with `DEFAULT_WEIGHTS` and `minSamples: 20`, `count = 80`:

| Source | n | min | median | max |
| --- | --- | --- | --- | --- |
| `generateHumanLike` | 50 | 0.778 | 0.843 | 0.884 |
| `generateReplayBot` over `generateHumanLike` | 50 | 0.699 | 0.767 | 0.822 |
| `generateGaussianBot` | 50 | 0.641 | 0.717 | 0.804 |
| `generateRandomJitterBot` | 50 | 0.515 | 0.567 | 0.594 |
| `generateConstantBot` | 1 (deterministic) | 0.139 | 0.139 | 0.139 |

The default single seed used by every test in `tests/analyzer.test.ts` sits near the middle of each of those ranges — `generateHumanLike(80)` scores `0.851`, `generateConstantBot(50)` scores `0.143`. Quote the range, not the seed.

## Step 1: Resolve the claim and check the preconditions

Restate the claim in one line and split it into sub-claims. If `$ARGUMENTS` is one sentence carrying two claims ("the new metric is cheaper **and** does not regress human scores"), that is two items.

Then, before gathering anything:

- `git status --short` and `git log --oneline -3` — record what the working tree actually contains. Evidence about an uncommitted change is only meaningful next to the diff that produced it.
- `npm run check`. If it fails, stop and say so — a failure downstream is about the build, not the behaviour.
- Read `.claude/worklog/` for a prior run on the same topic. A measurement already recorded is a rung 1 hit; do not re-derive it.
- Check whether `validation/` exists on this machine (`ls validation`). It is gitignored and absent from a fresh clone. Whether it is present decides whether rung 5 is available at all, and the report says which it was.

## Step 2: Build the checklist

One item per sub-claim, in the claim's own order, reusing its own wording as the label. Do not invent nicer labels; the label is the anchor back to the claim.

Drop anything not independently observable. Split a sub-claim that is really two.

## Step 3: Decide what each sub-claim is a claim about

Three shapes, and they need different evidence:

- **An accuracy claim** — "humans score above X", "this metric separates bots better". Needs a distribution, and its ceiling is set by where the input came from. This is the shape the ladder exists for.
- **A behaviour claim** — gating, lifecycle, the shape of a result, weight redistribution when a metric returns `NO_DATA`. The public `analyze()` result settles it, and a fixture input is fine here because the claim is about the code path, not about humans.
- **A platform claim** — `isTrusted`, passive listeners, SSR safety, bundle size, what Safari does. jsdom cannot settle any of these. `tests/integration.test.ts:297` measures `signals.syntheticEvents` as `5` precisely because `dispatchEvent` produces `isTrusted: false`; a real browser produces the opposite, and only a real browser can show it.

## Step 4: Gather evidence

Do the work; do not describe what should happen. Timebox each sub-claim to a few attempts.

**The surfaces, in order of what they can prove:**

- **The public `analyze()` result — the primary surface, and the only one that can produce ACCEPTED or REJECTED.** `score`, `metrics`, `signals`, `confident`, `sampleCount`, `classification`. That object is the contract consumers depend on.
- **An internal function's return value — diagnostic only.** A number out of `detectSpoof` (`src/anti-spoof.ts:122`) or `computeLogNormalityScore` explains *why* `flightFit` moved. It is not the contract. `flightFit` is `genuineScore` multiplied by an IKI-floor penalty (`src/analyzer.ts:151`), and the composite then redistributes weight across whichever metrics are not `NO_DATA` — so a `genuineScore` in isolation predicts nothing about `score`.
- **`snapshot()`** — the raw `dwells`, `flights`, `corrections`, `rollovers`, `total`, plus `events` when `recordEvents: true`. It is JSON-serializable, so a real browser session can be captured and replayed through `analyze()` offline. This is how a rung 4 run becomes a re-runnable number instead of a screenshot.
- **The demo's own UI** (`examples/react`). A reading, not a measurement — read the number, then get the same number out of `snapshot()` if the item depends on it.

### The unblock ladder

A sub-claim is BLOCKED only when every rung below is exhausted, or the missing piece is one only a human, a device or a dataset can supply. Do not stop at the first missing prerequisite.

1. **Evidence that already exists.** A prior run recorded in `.claude/worklog/`, a `CHANGELOG.md` entry, a test that already pins the behaviour. Read before you run. Free, and it is a real prior measurement rather than a staged one.
2. **The existing vitest suite over `tests/fixtures/`. Caps at EXERCISED, always.** Run it, read the real numbers, and name which generator produced them — `generateConstantBot`, `generateRandomJitterBot`, `generateGaussianBot`, `generateReplayBot`, `generateHumanLike`. They are seeded by a xorshift32 PRNG and therefore deterministic: a strength for regression (the same change moves the same number) and a weakness for accuracy (one seed is one sample).
3. **A new synthetic sweep. Still caps at EXERCISED.** Vary the fixture parameters — seed, `count`, correction and rollover rates — across a range and report the distribution rather than a point. It separates "the metric is wrong" from "we only ever tested one seed", which is the single most common way a fixture assertion lies. Write the sweep as a scratch `tests/*.test.ts`, run it with `npx vitest run <path>`, and delete it afterwards; the repo does not keep sweeps.
4. **The live demo in a real browser.** `cd examples/react && npm run dev`. `examples/react/vite.config.ts:11-12` aliases both entry points to `../../src`, so it exercises the **working tree, not the published package** — say so in the item. Typing into it produces real `KeyboardEvent`s with `isTrusted: true` and real `performance.now()` deltas from a real person's hands. This is the rung that converts most rows, and it earns **ACCEPTED for human-side claims**. Use the Chrome browser tools if they are available; otherwise hand the developer the exact URL, the exact field and the exact thing to type, and wait. Capture `snapshot()` so the run is re-runnable.
5. **The Aalto benchmark.** `npm run validate:aalto`. **Check first whether `validation/` exists on this machine** — it is gitignored and absent from a clone, and `tsx` is not in `devDependencies`, so the script fails at the runner before it reaches the data. If it is not there, say so plainly and do not pretend the rung was available. When it does run, it earns ACCEPTED for accuracy claims and it is the only rung that can. Record the real numbers, and record that they are not reproducible from a clone.
6. **Legitimately BLOCKED.** The ladder is exhausted and the missing piece needs a human, a device or a dataset. Name it. `BLOCKED (no Safari on a real iPhone)` reads very differently from `BLOCKED (didn't try)`.

Run rungs 1, 2 and 3 on your own initiative. **Rung 4 needs a word first when it means driving the developer's browser** — it opens tabs and takes the keyboard on their working machine. Rung 5 always says in the report whether the dataset was present.

### Record it verbatim

The literal command you ran and the literal output it returned, JSON trimmed to the fields the claim is about. Never reword a value into prose, and never reconstruct output from memory when drafting.

**Never fabricate a result.** Every score, count, median, spread and elapsed number in a draft comes from something you ran this session. If you could not gather it, say so at the gate — do not write a plausible-sounding item for a check you did not run.

**Read the source to explain a result, never to replace running it.** Finding out why `correctionRatio` reported `0` is a reason to read `scoreCorrectionRatio` and see the `NO_DATA` return at `src/analyzer.ts:193`. It is not a way to earn a verdict without calling `analyze()`.

## Step 5: Draft one report

Structure:

1. One opening line: the date, the commit or working-tree state, the `npm run check` result, and whether `validation/` is present.
2. One item per sub-claim, in the claim's order, headed `### <n>. <the sub-claim's own words> — <VERDICT>`.
3. Each item shows one check: `Ran:` then `Got:` then one line of reasoning. For an accuracy item, `Got:` is `n`, the median and the spread, with the generator or corpus named.
4. An item with more than one check gets a bold sub-label per check, each with its own blocks, and one shared reasoning line at the end.

**The four verdicts:**

| Verdict | What earns it |
| --- | --- |
| `ACCEPTED` | Measured on real human keystrokes captured through real browser events, or on a real external corpus. The only verdict that settles an accuracy claim. |
| `REJECTED` | Same bar, and what came back was wrong. |
| `EXERCISED` | The code did the right thing, but the input was synthetic or an in-repo fixture. Names what a real run would still add. |
| `BLOCKED` | Could not be run at all. The ladder is exhausted and the missing piece needs a human, a device or a dataset. |

**Style rules:**

- One report per run.
- First person, past tense, for what you did. Not "it was verified".
- Never repeat the claim. Reread it before finalising and cut any sentence that paraphrases it.
- No template phrases. Banned in spirit and verbatim: "As you can see", "Let's", "To see this yourself:", any sentence whose only job is to introduce the next one. `Ran:` / `Got:` is all the lead-in a block needs.
- A sub-claim with two halves gets its verdict scoped to the half you exercised; the other half is named as untested, not folded into a blanket ACCEPTED.
- Every metric name, constant, file path, threshold and number gets inline code: `flightFit`, `NO_DATA`, `src/analyzer.ts:20`, `0.717`, `minSamples`.
- As short as possible. A line each for the action, the output, the analysis. Cut every word that is not a fact.
- Plain words. Banned: leverage, robust, comprehensive, ensure, seamless, crucial, delve.
- No emoji, no sign-off, no bot attribution. It reads like the developer wrote it after testing.

## Step 6: Approval gate — STOP and ASK

Present:

- The checklist with each verdict, matched to its item.
- **Anything not ACCEPTED goes first, not buried.** For each EXERCISED or BLOCKED item that a ladder rung could still convert, the concrete plan next to it — which rung, which URL and field, what gets typed, how long it takes, what state the machine is left in.
- The full drafted report, exactly as it will be written.

```
**What you can do:**
- Reply 'go' (or 'approved' / 'write it') → I'll append this to .claude/worklog/
- Reply 'edit <n>: <what to change>' → I'll redraft item n and re-present the whole report
- Reply 'drop <n>' → remove that item
- Reply 'run it' → I'll run the prepared plan (a wider sweep, the live demo, the Aalto benchmark), then redo those items for real
- Reply 'cancel' → nothing is written
```

Then STOP and wait. **Never write without an unambiguous yes.**

## Step 7: Strip the development narrative

Run this on the final text every time. Delete:

- **Development history.** "the bug the review caught", "originally the analyzer", commit SHAs as narrative rather than as the state evidence was gathered against.
- **Design rationale.** Why the code is written this way. If the behaviour is right the reason is irrelevant here; if it is wrong, that is a bug, not a rationale.
- **Internal names in prose.** `scoreDwellVariance` inside a pasted stack trace: fine. A sentence comparing two internal functions: cut, unless it is the one-line explanation of a measured result.
- **Test-suite claims as evidence.** "the unit tests cover it" is not a verdict on accuracy. The one-line precondition at the top is the whole allowance.
- **Self-narration.** "this session", "I decided to", "instead of stopping at BLOCKED".
- **Effort commentary.** "this was tricky", "took several attempts".

Keep: what was run, what came back, the verdict, and the limits that affected testing.

Rewrite rather than delete when a banned line carries a real fact. "`correctionRatio` returns `NO_DATA` at zero corrections by design" becomes "the bot fixture reported `correctionRatio: 0` and its weight redistributed across the other five metrics" — same information, stated as observed behaviour.

## Step 8: Write to the worklog (only on approval)

There is no tracker in this repo. `CHANGELOG.md` is generated by `semantic-release` and records what shipped, never what was measured — so `.claude/worklog/` is the only place a measurement and its reasoning survive.

Append the report under the topic, in the format `/worklog` established. Create the directory and the topic file if neither exists yet. Append; never rewrite an earlier entry — a superseded measurement stays, with the new one below it and a line saying what changed.

Do not commit. The worklog entry is a working note, and a commit on `main` in this repo triggers `release.yml`.

## Step 9: Report

Print the worklog path and a one-line tally — "2 ACCEPTED, 0 REJECTED, 3 EXERCISED, 1 BLOCKED — the three EXERCISED rows need 90 seconds of typing in the demo". Say plainly that a claim with anything below ACCEPTED is not settled. This command records what was observed; the developer decides whether that is enough to ship.

## Guard rails (LLM-enforced)

- **Nothing is written to `.claude/worklog/` before the Step 6 approval.** Headline invariant.
- **No ACCEPTED without real browser events or a real external corpus.** A run against `tests/fixtures/` caps the item at EXERCISED, always, and the item says the input was synthetic and names what a real run would add.
- **A passing test is a precondition, never a verdict.** `npm run check` green means the change compiles and the fixtures still behave. It says nothing about accuracy.
- **Report distributions, not single scores.** An accuracy item carries `n`, a median and a spread, with the generator or corpus named. One score from one seed is not evidence.
- **No fabricated results.** Every score, count, median and elapsed number traces back to something run this session. If asked to go faster by skipping a check, refuse and say why.
- **Read-only by default.** Driving the developer's browser needs their word first — it takes the keyboard on their working machine. A scratch sweep file is deleted afterwards. Nothing in `src/` is edited.
- **This command verifies; it does not fix.** If evidence surfaces a bug, name it as a follow-up at the gate. Do not patch it inline.
- **Say when `validation/` is absent.** Never present rung 5 as available, or its numbers as reproducible from a clone, when the directory is not on this machine.
- No commit, no push. A push to `main` publishes to npm.
- No bot attribution, no "Generated with" footer, no emoji.

## What this command is NOT

- Not a bug finder — it checks that behaviour matches a claim. A bug found here is a follow-up.
- Not a fixer — `/cadence:build` makes the change this later provides evidence for.
- Not a benchmark harness — it runs the benchmark that exists (`npm run validate:aalto`) and reports whether it could. Building a new corpus or a new runner is not this command's job.
- Not a release decision — the `releasing` skill owns whether a measured result is good enough to publish, and what the commit type does.
- Not a sign-off — it records what was observed; the developer decides whether the claim is settled.
